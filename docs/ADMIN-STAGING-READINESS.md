## Исправление стабильной загрузки

Исходная ветка: `feature/admin-marketplace-control-center`,
коммит `7dee59f83109bd3cff8e1bb965643c6e72739e2b`.

После ошибки `/api/admin/dashboard` интерфейс сбрасывал `loading`,
а зависимый от него эффект немедленно повторял запрос. При входе загрузка
также запускалась из двух мест. Это вызывало мигание и поток запросов.

Исправление запускает первоначальную загрузку при подтверждённом входе.
После ошибки повтор выполняется кнопкой «Обновить данные». При обновлении
уже загруженные данные сохраняются. Выход и новый запрос отменяют устаревшее
чтение; его ответ не должен менять состояние кабинета.

Проверки находятся в `tests/e2e/admin-dashboard-loading.spec.js`:

- ошибки 502 и 403, некорректный ответ и обрыв соединения;
- повторная загрузка по кнопке;
- вход, истечение доступа и повторный вход;
- сохранение данных при неудачном обновлении;
- выход во время загрузки и запоздавший ответ.

Команды из корня репозитория:

```bash
npm ci --ignore-scripts
npm --prefix frontend ci --ignore-scripts
npx playwright install chromium
npx playwright test --config playwright.admin.config.js
```

Проверки открывают настоящую страницу Next.js, но подменяют ответы её API.
Адрес CMS направлен на закрытый локальный порт. Эти проверки не подтверждают
работу настоящей базы, прав доступа, писем или оплаты.

Автоматическая проверка описана в `.github/workflows/admin-dashboard.yml`.
Она запускается для запросов на слияние в тестовую ветку и не получает секреты.

Локальная проверка 13 сентября 2026 года:

- исходный код: проверка остановки повторов обнаружила 70 запросов вместо одного;
- исправленный код: все 7 браузерных проверок прошли;
- 40 существующих проверок кабинета и входа прошли;
- TypeScript `tsc --noEmit --incremental false` прошёл.

Браузерная проверка выполнена в Chromium 153 с Playwright 1.61.
Проверка на GitHub и проверка развёрнутого сайта — отдельные результаты.

## Применение

Ветка `fix/admin-dashboard-load-lifecycle` предназначена для проверки кода.
Её автоматическое развёртывание отключено в `vercel.json` в корне и в
`frontend/vercel.json`, чтобы оба варианта корня проекта соблюдали это правило.
Причина: настройки тестовой CMS привязаны к конкретной ветке
`feature/admin-marketplace-control-center`, а новая ветка их не наследует.
Остальные ветки этим правилом не отключаются.
Поведение описано в [документации Vercel](https://vercel.com/docs/project-configuration/git-configuration).

После проверки изменение должно попасть в существующую тестовую ветку.
На её новом развёртывании нужно проверить вход, переключение разделов,
однократную загрузку и повтор по кнопке с настоящей тестовой CMS.
Готовность локальных проверок не означает, что изменение уже применено на сайте.

## Данные и резервные копии

По проверкам пользователя 11 сентября 2026 года основная база сохранена:
15 строк лодок, 28 строк маршрутов, 3 владельца, 2 заявки, 29 записей файлов.
Число строк может включать языковые версии и не равно числу отдельных лодок.
В новой отдельной тестовой базе есть один администратор; контент в неё
не переносили. Пустой тестовый кабинет не означает удаление основной базы.

Три архива баз восстановлены в отдельном PostgreSQL 16 на Mac;
проверенные количества строк совпали. Архив основных загрузок содержит
580 файлов. Копии есть на сервере и на Mac, контрольные суммы совпали.
Это не проверка восстановления ролей, секретов и всех связей записей с файлами.
Автоматическое регулярное копирование ещё требует настройки.
